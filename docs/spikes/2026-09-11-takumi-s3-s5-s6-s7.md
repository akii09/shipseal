# Spike record: S3, S5, S6, S7

Date: 2026-09-11 · Questions: `PROJECT_PLAN.md` §24 · `takumi-js@2.13.7`, `shiki@4.4.3`
Machine: Apple M5, Node v22.22.3. Spike code lived in `spikes/s3-s5-s6-s7/` and has been deleted.

Three questions are fully answered. **S3 is partially answered**: the platform matrix and the WASM fallback are verified, but an actual GitHub runner has not been exercised, because that needs a workflow run and agents do not push.

---

## S3: does the native binary run on the runners, and is there a WASM fallback?

**Prebuilt binaries.** `@takumi-rs/core@2.13.7` declares eight platform packages as optional dependencies:

```
darwin-x64      darwin-arm64
linux-x64-gnu   linux-x64-musl
linux-arm64-gnu linux-arm64-musl
win32-x64-msvc  win32-arm64-msvc
```

That covers every GitHub-hosted runner (`ubuntu-latest` x64 gnu, `windows-latest` x64 msvc, `macos-latest` arm64), the ARM runners, and musl for Alpine containers. `darwin-arm64` resolved and ran here.

**WASM fallback is real and usable.** `takumi-js/wasm` exports `init()`, `initSync()` and a `Renderer` class with `render`, `renderSvg`, `measure`, `renderAnimation`, `registerFont`. Note it does **not** export a bare `render()` function the way the main entry does.

| Backend | Cold | Warm median | Output |
|---|---|---|---|
| native | 18 ms | 3.1 ms | 9,337 bytes |
| wasm | 49.5 ms | 7.0 ms | 9,337 bytes |

WASM is 2.3x slower and still an order of magnitude inside budget. **The two backends produced byte-identical output** (same sha256), which means a WASM fallback does not break the determinism promise in §3 or the golden image tests in §20.

**Not verified:** a real run on `ubuntu-latest`, `windows-latest`, or `macos-latest`. The binaries are published and the CI workflow already runs `pnpm test` on `ubuntu-latest`, so the first render added to the test suite will answer it. Treat the platform support statement as "published for, not yet exercised on" until then.

## S5: can Takumi render a code card of shiki tokens fast enough?

**Yes, comfortably.** `shiki@4.4.3` (MIT). A 13 line TSX snippet produced **80 colored spans**.

| Load | Render time |
|---|---|
| 13 lines, 80 spans, 1200x675 | 7.5 ms median (min 6.2, max 11.6 over 10 runs) |
| 26 lines, 160 spans | 12.9 ms |
| 52 lines, 320 spans | 26.3 ms |

Cost is linear at roughly 0.08 ms per span. The §14.3 limit of about 14 lines is nowhere near a problem; even a 52 line card renders in 26 ms.

**Defect found: leading whitespace collapses, so code indentation is lost.** Measured width of a single character preceded by 0, 2, 4 and 6 spaces:

| Strategy | Widths (0 / 2 / 4 / 6 spaces) | Result |
|---|---|---|
| raw spaces in the text node | 13, 26, 26, 26 | **collapses to one space** |
| `whiteSpace: "pre"` on the text node | 13, 40, 66, 92 | **correct, 13 px per space** |

The first render of the code card visibly flattened a nested JSX block to one space of indent. **Every text node in the code card must set `whiteSpace: "pre"`.** A golden image test should cover a snippet with at least three indent levels.

## S6: PNG vs WebP per format, and do platforms accept WebP?

Same hero card rendered at all eight §14.2 sizes:

| Format | Size | PNG | WebP | Saving | PNG ms | WebP ms |
|---|---|---|---|---|---|---|
| og | 1200x630 | 36.5 KB | 16.9 KB | 54% | 6 | 90 |
| github-social | 1280x640 | 39.5 KB | 16.9 KB | 57% | 6 | 90 |
| x | 1200x675 | 38.3 KB | 16.6 KB | 57% | 6 | 99 |
| linkedin | 1200x627 | 36.6 KB | 16.9 KB | 54% | 5 | 86 |
| square | 1080x1080 | 48.3 KB | 16.4 KB | 66% | 8 | 132 |
| portrait | 1080x1350 | 48.5 KB | 16.9 KB | 65% | 9 | 168 |
| producthunt | 1270x760 | 42.3 KB | 16.6 KB | 61% | 6 | 101 |
| readme-banner | 1280x400 | 30.4 KB | 16.7 KB | 45% | 4 | 65 |
| **whole pack** | | **320.5 KB** | **133.9 KB** | **58%** | | |
| code-card | 1200x675 | 33.5 KB | 14.2 KB | 58% | | |

WebP is 58% smaller and about 15x slower to encode. Both are fast in absolute terms.

**Platform acceptance settles it.** GitHub's own documentation says a repository social preview must be **PNG, JPG or GIF, under 1 MB**. WebP is not an accepted upload format.

Every PNG here is at most 48.5 KB, so the 1 MB cap is not close to binding and the size win buys nothing that matters. **PNG stays the default.** WebP remains available through `output.imageFormat` for users posting where they control the upload.

## S7: how reliably can Tailwind v4 `@theme` colors be extracted statically?

**Reliably.** 44 real `@theme` files were collected from public repositories via GitHub code search and run through a conservative parser: brace matching to find `@theme` and `@theme inline` blocks, a property regex for `--color-*`, and up to three levels of same-file `var()` resolution. No code execution, no CSS library.

| Measure | Result |
|---|---|
| files with a parsable `@theme` block | 44 of 44 (100%) |
| files yielding at least one `--color-*` | 42 of 44 (95%) |
| files with a `primary`, `brand` or `accent` color | 36 of 44 (82%) |

**Color value formats across 1,042 extracted values:**

| Format | Count | Share |
|---|---|---|
| `oklch()` | 538 | 51.6% |
| hex | 298 | 28.6% |
| `rgb()` | 149 | 14.3% |
| `hsl()` | 57 | 5.5% |

**oklch is the majority format**, so brand detection is useless without an oklch converter. It does not need a dependency: a 30 line oklch to sRGB hex function matched `culori` **exactly on 9 of 9 test values**, including percentage lightness, zero chroma, and both extremes.

The most common `--color-*` names map straight onto the §10.2 brand schema: `primary` (83), `secondary` (50), `background` (34), `accent` (34), `foreground` (22), `muted` (22). `chart` (90) is the most frequent and should be ignored.

**The one failure mode** is cross-file indirection: both failures defined `--color-primary-50: var(--ui-color-primary-50)` where the target lives in another file. The parser correctly declines to guess. `init` should report the color as not found rather than invent one.

---

## What these spikes change

1. Code card text nodes need `whiteSpace: "pre"` (S5).
2. PNG stays the default output format (S6).
3. Brand detection needs a built-in oklch to hex converter, no dependency (S7).
4. Platform support is "published for" not "exercised on" until a render runs in CI (S3).
