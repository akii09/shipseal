# Spike record: S1, S2, S4 (Takumi)

Date: 2026-09-11 · Questions: `PROJECT_PLAN.md` §24 · Package under test: `takumi-js@2.13.7`
Machine: Apple M5, Node v22.22.3, macOS arm64. Spike code lived in `spikes/takumi-s1-s2-s4/` and has been deleted.

All three questions are answered. Two findings contradict the plan and are corrected in §7 and §15.3.

---

## S1: current package name and render API. Does JSX require React at runtime?

**Package:** `takumi-js@2.13.7`, license `(MIT OR Apache-2.0)`, 63 KB unpacked, published 2026-09-06.
Dependencies: `@takumi-rs/core` (native, resolves a per-platform binary; `@takumi-rs/core-darwin-arm64` here), `@takumi-rs/wasm`, `@takumi-rs/helpers`.

That `@takumi-rs/wasm` is a plain dependency and not optional is a partial answer to S3: a WASM fallback ships in the box.

**Entry points** (from the package's own `exports`):

| Subpath | Contents |
|---|---|
| `takumi-js` | `render`, `renderSvg`, `renderAnimation`, `setGlyphCacheMaxBytes` |
| `takumi-js/node` | re-exports `@takumi-rs/core`, including the `Renderer` class |
| `takumi-js/helpers` | `container`, `text`, `image`, `googleFonts`, `fontFromUrl`, `subsetFonts` |
| `takumi-js/wasm`, `takumi-js/wasm-url` | WASM backend |
| `takumi-js/response` | `ImageResponse` |

**Render signature:**

```ts
render(element: RenderInput, options?: RenderOptions): Promise<Buffer | Uint8Array>
type RenderInput = ReactNode | ReactElementLike | Node | string
```

**Answer: React is not required at runtime.** Four input shapes were rendered with zero react packages installed:

| Input | Result | Time |
|---|---|---|
| Takumi node tree via `container()` / `text()` | 9,883 bytes | 669.6 ms cold |
| `ReactElementLike` plain object `{type, props, key}` | 9,550 bytes | 7.0 ms |
| HTML string | 7,478 bytes | 6.6 ms |
| Real `.tsx` compiled by `tsc` | 11,555 bytes | rendered correctly |

The `.tsx` path works by pointing `jsxImportSource` at a local four-line module:

```js
const jsx = (type, props, key) => ({ type, props, key: key ?? null });
export { jsx, jsx as jsxs, jsx as jsxDEV };
export const Fragment = Symbol.for("takumi.fragment");
```

`tsc` then emits `import { jsx as _jsx, jsxs as _jsxs } from "takumi-jsx/jsx-runtime"`, and `fromJsx()` accepts the result because it only needs the `ReactElementLike` shape. Compile and render both verified end to end.

**One constraint:** Takumi's `.d.ts` files import from `react` and `csstype`. With `skipLibCheck: false` typecheck fails with 12 errors in `node_modules`. With `skipLibCheck: true`, which `tsconfig.base.json` already sets, typecheck is clean with no react types installed. Keep it true.

**Determinism** (§3 principle 2, §20): byte-identical across two renders in one process, and byte-identical across two separate processes. Same sha256.

**Performance** (Phase 1 criterion: under 500 ms for 1200x630, excluding first-run font load): cold 88.7 ms, warm median 4.3 ms, max 5.3 ms over 10 runs on a realistic release-hero card. **PASS with two orders of magnitude of headroom.**

## S2: does takumi-js expose text measurement to JavaScript?

**Answer: yes.**

```ts
import { Renderer } from "takumi-js/node";
renderer.measure(source: Node, options?: RenderOptions, signal?: AbortSignal): Promise<MeasuredNode>

interface MeasuredNode  { width: number; height: number; transform: [number,number,number,number,number,number];
                          children: MeasuredNode[]; runs: MeasuredTextRun[] }
interface MeasuredTextRun { text: string; x: number; y: number; width: number; height: number }
```

**There is no line-count field.** Derive it by walking the tree and counting distinct rounded `run.y` values. Do not use `runs.length`: it happens to equal the line count only for text in a single style, and a code card with colored inline spans will emit several runs per line.

Measured in a 1040 px box (1200 minus the §14.2 safe zone), `lineHeight: 1.1`:

| Font size | Lines | Height |
|---|---|---|
| 72 | 4 | 317.0 |
| 68 | 4 | 300.0 |
| 64 | 4 | 282.0 |
| 60 | 3 | 198.0 |
| 56 | 3 | 185.0 |
| 48 | 3 | 159.0 |

The derived line count tracks the height break exactly, so it is trustworthy.

**Integration detail:** `measure()` takes a Takumi `Node`, not JSX. The fitting pass must call `fromJsx()` from `@takumi-rs/helpers/jsx` first, which returns `{ node, css }`. Verified: a JSX element measured to `{width: 1040, height: 238, lines: 3}` with line y-values `[-7, 72, 151]`, spaced 79 px apart, which is 72 x 1.1 as expected. The first y is negative because it is a baseline offset, which does not affect counting.

**Cost:** 20 `measure()` calls in 2.7 ms total, roughly 0.14 ms each. The §15 loop walks at most 7 sizes per slot per format, so fitting is free. No caching needed.

**Consequence for §15.3:** the fallback plan of measuring with a font-parsing library is not needed, and neither is the dependency it would have required under R7. §15.3 is updated.

## S4: which fonts are bundled, and how are custom fonts loaded?

**Answer: exactly one family is bundled, Geist, in weights 300 to 800.**

The same string was rendered under nine family names. Every one produced byte-identical output, meaning every one fell back to the same bundled face:

```
Geist, Geist Mono, Inter, Arial, Helvetica,
ThisFontDoesNotExist, serif, sans-serif, monospace
  -> all hashed 8b5991122821
```

Weights 300, 400, 500, 600, 700 and 800 each render differently; 900 is identical to 800, so it clamps.

**This contradicts plan §7**, which claimed Geist and Geist Mono are both bundled. **Geist Mono is not bundled.** The code card (§14.3) and `brand.fonts.mono` (§10.2) both assume a mono face, so Shipseal has to supply one. §7 is corrected. The question of how to supply it is left open in §25.

**Custom font loading works.**

```ts
type Font = FontDetails | ByteBuf
interface FontDetails { name?: string; data: ByteBuf; weight?: number; style?: string; subsetOf?: string }

await render(node, { width, height, fonts: [{ name: "ShipsealMono", data: bytesFromDisk }] })
```

- Raw bytes read from disk work, which is the path `brand.json` `fonts.*.file` needs.
- **WOFF2 is confirmed working**: a 2,824 byte file with `wOF2` magic rendered correctly, visually monospaced with a slashed zero.
- `googleFonts(["Geist Mono"])` returns 6 unicode-range coverage subsets in about 208 ms. It fetches over the network at load time, so it cannot serve the default offline path and it sits badly with §16.2 ("no network fetches during render").

**Sharp edge worth a template rule.** Registering any custom font changes the family used by text nodes that do not set `fontFamily`:

```
bare text, no fonts registered : ab72b86e596c
bare text, mono registered     : ef3d07eedd93   <- silently restyled
text pinned to fontFamily "Geist", either way : ab72b86e596c
```

So loading a user's brand mono font would silently restyle every heading that forgot to name a family. **Every text node in a Shipseal template must set `fontFamily` explicitly.** A golden image test should cover a template rendered with and without a custom font registered.

## Open questions this spike raises

1. **How does Shipseal supply Geist Mono?** Vendor the file into the package (adds bytes to the npm tarball, needs an OFL notice), fetch it at `init` time and cache it under `.shipseal/`, or drop the mono default and require the user to point at a file. This is a dependency and licensing call, so it needs an owner decision.
2. **§16.1's adapter interface does not match reality.** It declares `measureText?(text, opts): Promise<{lines, width, height}>`, taking a string and a font. Takumi measures a node tree. The adapter can still offer that convenience by building a node internally, but the signature needs revising, and that is a public interface change requiring approval.
