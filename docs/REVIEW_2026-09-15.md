# Review 2026-09-15: 20 real repositories

Shipseal 0.1.1 was run against 20 public repositories through the same code path `/try` uses
(`listPublicReleases` to `collectPublicRelease` to `buildStudioPack`), rendering both a story pack
and a release pack for each. Three were also driven through the browser at shipseal.dev.

**Nothing crashed.** 18 of 20 produced a full pack. Tag shapes that all parsed correctly:
`v16.0.0`, `astro@7.3.2`, `3.9.6`, `nightly`, `bun-v1.4.2`, `shadcn@4.21.0`, `2026.9.2`,
`v1.20.1-pre`. The renderer, the fitter, the PDF and the ZIP held up on every one.

The problems are not in rendering. They are in what the card ends up saying.

## R0. The demo shows every repository in Shipseal's own colors, with no logo

> **Done 2026-09-15.** Detection split into `brand/detect-colors.ts` (source agnostic) and
> `brand/detect-node.ts` (disk), with `sources/github-files.ts` supplying the GitHub reader.
> Verified live: `shadcn-ui/ui` detects `#e5e5e5` from Tailwind v4 `@theme`, `typst/typst`
> detects `#239dad` from `:root` variables. Logo remains out of scope in the browser.

This is the most damaging finding and it affects **100% of repositories**, not a subset.

`DEFAULT_BRAND_COLORS.primary` is `#ff4d4d`. Shipseal's own primary is `#fb4c4b`. The background,
foreground, muted and accent values are byte-identical. So unless a repository already contains a
`.shipseal/brand.json`, which essentially none do, its card renders in Shipseal's palette.
`brand.logo` was missing on all 20.

The cause is that `sources/public-repo.ts` performs **no detection at all**. It looks for a
committed brand file and otherwise falls back to defaults. Meanwhile the CLI carries a proven
detection suite it never calls: `brand/detect.ts` (CSS custom properties, `tailwind.config.*`,
`*.tokens.json`, `package.json`), `brand/tailwind.ts`, `brand/css-vars.ts`, `brand/color.ts` with
its oklch converter, and `brand/logo.ts`. Spike S7 measured that suite at 95% of real Tailwind
`@theme` files yielding colors and 82% carrying a usable brand color.

The page does disclose it: "These are demo colors; choose your accent below." So this is honest
rather than deceptive. It is still the wrong outcome, because the entire pitch of `/try` is *your*
release in *your* colors, and what a visitor actually sees is a red Shipseal card with their text
in it. The accent picker asks them to do by hand the one thing the product claims to do for them.

**Why detection cannot simply be called today:** `detect.ts` walks the filesystem with `readdir`
and `readFile`. The fix is to invert that dependency, so detection takes a "list files" and "read
file" pair instead of touching disk, with the CLI supplying the disk implementation and the demo
supplying a GitHub-backed one (git trees API to list, contents API to read). One implementation
then serves both surfaces, which is the same lesson as R1.

**Cost to watch:** an unauthenticated visitor has 60 GitHub requests per hour. A tree call plus a
few file reads per repository is affordable, but it must be bounded and cached per repository.

**Logo:** even when a brand file is found the logo is deliberately dropped, because the browser
cannot read repository files. The same GitHub-backed reader would fix that, with SVG handled
through the existing `brand/png.ts` path.

## R1. Two cleaners, two sets of rules

> **Done 2026-09-15.** One `sources/release-line.ts`, used by both paths.

`cleanChangelogItem` (the CLI path) strips 14 patterns: commit hashes, `(#123)`, `[#123](url)`,
`Thanks @user`, bare `@handles`, trailing periods. `cleanBullet` (the `/try` path) strips 5:
images, links, HTML, asterisks and backticks. Everything else survives.

That single divergence produced the worst result in the survey. `oven-sh/bun` rendered a card whose
headline was **`@dylan-conway`**, a contributor's GitHub handle, because the release body opens with
a credit line. A Bun maintainer opening `/try` sees that first.

`astral-sh/ruff` rendered `\[ruff\] Recognize re.prefixmatch (RUF039, RUF055) (`, keeping
backslash-escaped brackets and cutting mid-parenthesis.

**Fix:** one cleaner, shared by both sources, with the union of the rules plus markdown unescaping.
This is the highest-value change in this document and it is not a large one.

## R2. Releases-only discovery excludes major projects

`golang/go` and `python/cpython` both failed with `demo.no-releases`. Neither publishes GitHub
Releases; they ship git tags. Two of the most recognisable repositories in the world cannot use the
demo or the Action.

**Fix:** fall back to tags when a repository has no releases, using the tag and its commit date.
Fewer facts are available, and the manifest should say so.

## R3. The monorepo fallback headline reads badly

When every entry maps to a fix, the headline falls back to `{brand name} {version}`. For a monorepo
the detected name is the directory, so `shadcn-ui/ui` rendered **`ui shadcn@4.21.0`**,
`home-assistant/core` rendered **`core 2026.9.2`**, and `supabase/supabase` rendered
**`supabase 1.26.08`**.

**Fix:** prefer the repository name over a bare directory name, and drop the duplicated package
prefix already present in the tag.

## R4. Titles truncate often

Story change-page titles truncated on 6 of 20 repositories, three times on `withastro/astro` alone.
Every one raised a manifest warning, so nothing shipped silently, but a truncated title is a card
nobody posts. Release bullets are routinely longer than a card headline.

**Fix:** pick the most headline-shaped entry rather than the first, and allow a fourth line on tall
formats before truncating.

## R5. Prereleases are chosen as the default

`zed-industries/zed` defaulted to `v1.20.1-pre`. The selector lists prereleases, which is correct,
but the default should be the newest stable release.

## R6. The seal loses its commit count on every public repository

`release.commitCount` was missing for all 20. The demo has no git history, so the seal renders
`sealed · <date>` with no commit segment. Correct behaviour, but it means the verified-facts mark
is weakest exactly where a new visitor first sees it. Worth deriving from the compare API.

## Plan for the next major

Ordered by what a new adopter hits first.

| | Item | Why |
|---|---|---|
| 1 | **Brand detection over the GitHub API** (R0) | Every demo card currently wears Shipseal's colors. Biggest gap between what `/try` promises and what it shows |
| 2 | **Unify the two cleaners** (R1) | Removes `@handle` and escaped-markdown headlines. Best value per line changed |
| 3 | **Tag fallback when no releases exist** (R2) | Unlocks Go, CPython and every tag-only project |
| 4 | **Headline selection, not first-entry** (R4) | Fewer truncated titles, better cards without new UI |
| 5 | **Monorepo naming** (R3) | Stops `ui shadcn@4.21.0` |
| 6 | **Default to the newest stable release** (R5) | One-line change |
| 7 | **Commit count from the compare API** (R6) | Restores the seal on the demo |

Items 2, 5 and 6 are small. Item 1 is the largest piece of work here and the most valuable: it
refactors brand detection to be source agnostic. Items 3 and 7 add a source and change the facts
shape, so they need the owner's sign-off, and 7 overlaps the open partial G8.

## What did not need fixing

The renderer, text fitting, overflow warnings, the PDF carousel, the ZIP, tag parsing, and the
emoji stripping shipped in 0.1.1. Brand detection works well in the CLI; it is simply not reachable
from the demo. Every failure above is in
turning a release body into a sentence, which is the part that depends on other people's
conventions rather than on our own code.
